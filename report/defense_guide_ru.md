# Подготовка к защите SIS2

## Суть работы за 30 секунд

Мы построили конвейер обработки записей о биоразнообразии Казахстана из GBIF. Данные собираются через API, проходят через Apache Kafka, проверяются Pandera, очищаются с pandas и NumPy, сохраняются в SQLite и затем анализируются. На сохранённом запуске из API пришло 1 053 записи, а в итоговой базе осталось 1 031: одна реальная запись не прошла валидацию и 21 повторное наблюдение удалено при очистке.

## Речь на 2–3 минуты

«Цель проекта — получить реальные наблюдения видов из Казахстана и провести их через воспроизводимый конвейер сбора, потоковой передачи, проверки, подготовки и анализа. Источник — открытый GBIF Occurrence API. Мы брали данные за 2015–2025 годы: до 8 записей для каждого сочетания года и месяца. Это исправило проблему первого варианта выборки, где из-за порядка выдачи API почти все записи попадали на январь. Сырой ответ сохраняется отдельно и далее не изменяется.

Затем producer отправляет записи в Kafka как JSON-сообщения с Pydantic-контрактом. Consumer получает их, проверяет структуру сообщения и сохраняет в CSV. После записи он подтверждает offset. Для демонстрации обработки ошибок мы дополнительно отправили три заведомо сломанных сообщения: consumer их отклонил.

Следующий этап — Pandera. Она проверяет уже таблицу: обязательные поля, допустимые категории, диапазоны координат и дат, а также согласованность года с датой наблюдения. Три специально испорченные строки тоже были обнаружены и не попали дальше. Из 1 053 реальных записей одна была отправлена в карантин из-за отсутствующих таксономических полей.

На этапе подготовки мы привели типы и названия регионов к единому виду, обработали пропуски, удалили 21 повторное наблюдение, добавили вычисляемые признаки и построили агрегаты. Осталась 1 031 запись. SQLite использует `gbif_id` как первичный ключ и UPSERT с хешем содержимого: повторная загрузка тех же данных не создаёт дублей и не меняет записи. Анализ читает именно базу и строит шесть графиков. Итог проверяется 12 проверками согласованности; в сохранённом запуске все прошли».

Если времени мало, оставьте из речи цель, цепочку этапов, цепочку чисел и одно ограничение выборки.

## Типовые вопросы и короткие ответы

1. **Почему GBIF?** Это открытый API с реальными географическими, временными и таксономическими полями; данные достаточно разнообразны, чтобы показать проблемы качества.
2. **Почему выборка по году и месяцу?** Начало выдачи API было смещено в сторону января. Квота до 8 записей по 132 слоям (11 лет × 12 месяцев) позволяет сравнивать состав выборки по месяцам. В трёх слоях нашлось меньше 8 записей, поэтому всего получилось 1 053. Это не случайная выборка из всей базы GBIF.
3. **Что делает Kafka в проекте?** Producer публикует JSON в topic с тремя partitions, consumer читает сообщения. Это реальная передача через брокер, а не прямой вызов между модулями.
4. **Зачем Pydantic и Pandera одновременно?** Pydantic проверяет форму одного сообщения при отправке/получении; Pandera проверяет строки и правила табличного набора, включая связи полей.
5. **Что происходит с ошибочными данными?** Некорректные сообщения отбрасываются consumer; некорректные строки Pandera сохраняются в `data/invalid_records.csv` и не попадают в очистку и БД.
6. **Что означает подтверждение offset после сохранения?** При падении до подтверждения сообщение может прийти повторно. Это режим *at least once*, поэтому повторы дополнительно устраняются при очистке и загрузке.
7. **Как искали дубликаты?** Сначала по `gbif_id`, затем по сочетанию научного названия, округлённых координат и дня наблюдения. Из повторов оставляли запись с более точной координатой, затем с большим числом медиа.
8. **Как обрабатывали пропуски?** Регион нормализовали и иногда определяли по ближайшей размеченной точке в пределах 50 км; неопределённость координат заполняли медианой группы `basis_of_record` и ставили флаг `uncertainty_imputed`; отсутствующий `individual_count` заполняли единицей.
9. **Что значит идемпотентная загрузка?** Тот же CSV можно загрузить второй раз: первичный ключ и UPSERT не создают новых строк, а сравнение `row_hash` не обновляет неизменённые данные. В сохранённом тесте повторно было 0 вставок и 0 обновлений.
10. **Главные выводы анализа?** В итоговой выборке 69,1% записей относятся к птицам; найдено 27 записей о 8 видах из угрожаемых категорий IUCN; всего 461 вид. Выводы относятся к собранным данным, а не ко всем видам Казахстана.
11. **Можно ли утверждать, что птицы чаще встречаются в природе или что летом их объективно больше?** Нет. Данные GBIF зависят от активности наблюдателей; равная квота по месяцам делает график сезонного состава непригодным для оценки абсолютного числа наблюдений по сезонам. Рост числа записей по годам оценивали отдельно по GBIF facet counts.
12. **Ограничения архитектуры?** Один Kafka broker, без репликации и защиты; данные API меняются со временем; 583 значения неопределённости координат в очищенном наборе были восстановлены и помечены флагом.

## Что показать на экране

1. Схему в `docs/architecture.svg` и кратко пройти по стрелкам.
2. `data/summaries/pipeline_verification.txt`: показать цепочку чисел и 12 строк `[PASS]`.
3. `data/invalid_records.csv`: показать отдельный карантин для ошибок валидации.
4. `data/pipeline_stats.json`: показать результат повторной загрузки.
5. Пару графиков из `figures/`, например состав по месяцам и угрожаемые виды; проговорить ограничения выборки.

Для живого запуска по данным репозитория: `docker compose up -d`, затем `uv sync`, затем `uv run python main.py --skip-collect`. Нужен работающий Docker/Kafka. `--skip-collect` использует сохранённые сырые данные и не делает новых запросов к GBIF. Перед демонстрацией убедитесь, что Kafka здоров и достаточно времени для выполнения конвейера.
